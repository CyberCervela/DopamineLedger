# ARCHITECTURE.md — Dopamine Ledger, round 2

How the code is organized, why, and where each kind of logic belongs.

---

## Layer cake

```
┌───────────────────────────────────────────────────────────┐
│  Views (SwiftUI)                                          │
│  Consume Theme via @Environment. No business math.        │
├───────────────────────────────────────────────────────────┤
│  Services (SessionFinalizer, NotificationScheduler, ...)  │
│  Touch SwiftData + system APIs. Apply math layer results. │
├───────────────────────────────────────────────────────────┤
│  Math (SessionMath, RepayMath, NotificationMath)          │
│  Pure functions. No SwiftData, no system APIs. Testable.  │
├───────────────────────────────────────────────────────────┤
│  Models (@Model classes)                                  │
│  SwiftData persistence + a few computed helpers.          │
└───────────────────────────────────────────────────────────┘
```

The rule: **every layer can call down, none calls up.** Models don't
know about services; services don't know about views; views don't know
about persistence beyond `@Query` and `ModelContext`.

## The Theme protocol — the central round-2 change

In round 1, `Theme` was a single struct of static values; views read
`Theme.spendColor`, called `Image(systemName:)` directly, and (later)
also called `IconResolver.image(for:)` which returned an SF Symbol. The
result was a view layer that was structurally bound to one rendering
style. Switching to pixel art meant editing dozens of views.

Round 2 fixes this at the root. `Theme` is a protocol:

```swift
protocol Theme {
    var colors:     ThemeColors      { get }
    var typography: ThemeTypography  { get }
    var spacing:    ThemeSpacing     { get }
    func icon(_ named: SemanticIcon) -> Image
    func sound(_ named: SemanticSound) -> SoundAsset?
    var usesPixelArtRendering: Bool { get }
}
```

Two implementations ship from day 1:

- **`SystemTheme`** — system fonts, semantic system colors, SF Symbols,
  default UISounds. Looks like a "normal" iOS app. Good baseline,
  great for accessibility/Dynamic Type.
- **`PixelArtTheme`** — Monogram + AbaddonBold fonts, dark-navy palette,
  pixel-art assets via `IconResolver`'s asset-catalog branch, themed
  sound effects. The intended primary experience.

Selection is via `@Environment(\.theme)`. The app root injects the active
theme; `SettingsView` flips it. Views are read-only consumers:

```swift
@Environment(\.theme) private var theme
// ...
Text("Balance")
    .font(theme.typography.title)
    .foregroundStyle(theme.colors.textPrimary)
theme.icon(.charger).resizable().frame(width: 32, height: 32)
```

See `DESIGN_SYSTEM.md` for the catalog of semantic roles
(`ThemeColors`, `ThemeTypography`, `ThemeSpacing`, `SemanticIcon`,
`SemanticSound`).

## Pure-function math modules

`SessionMath`, `RepayMath`, `NotificationMath` are `enum`s with `static`
functions. They take primitives in, return small `struct` outcomes, and
never touch SwiftData or system APIs. This is the **only** layer where
business math lives — view code never inlines a "credits per second"
multiplication.

Why: testability. `DopamineLedgerTests` covers all three modules without
spinning up a `ModelContainer`. When a rule changes (e.g. "make debt
penalty 1.5× instead of 2×"), there is exactly one file to edit.

If you find yourself reaching for new business math in a service or
view: extract a `*Math.swift` first.

## Service helpers

Two services exist because two call sites needed the same side-effectful
flow. Add a new service only when a second call site emerges — don't
pre-extract.

- **`SessionFinalizer`** — used by `SessionView` (Stop button) and
  `SettingsView` (Stop active session). One function:
  `finalize(session:, in: ModelContext) -> FinalizedSession?`. Wraps
  notification cancel + math + ledger + debt insertion.
- **`NotificationScheduler`** — wraps `UNUserNotificationCenter` for
  schedule and cancel of the warning/alarm pair, plus permission prompt.
  Identifiers are prefixed (`session.warning.<uuid>`, `session.alarm.<uuid>`)
  so cancel-by-session-id is trivial.

`SoundPlayer` will become a third service when the pixel-art theme starts
playing sound effects. The scaffolded file is a stub.

## SwiftData notes

- **Singleton `Ledger`.** `Ledger.fetchOrCreate(in:)` is `@MainActor` and
  returns the one-and-only row, creating it on first read.
- **Denormalized `activityId` on `Session` and `ActivityDebt`.** A direct
  `@Relationship` was hard to query from `@MainActor` views without a
  `MainActor.assumeIsolated` dance; storing the UUID avoids the noise.
- **`#Predicate` cannot close over nested property access.** Always extract
  to a local first — see `TOOLING.md` for the recipe.

## What this rebuild is consciously NOT doing

- **No view-model layer (yet).** Round 1 used `@Query` + `ModelContext`
  directly in views; round 2 continues that until proven painful. The
  service helpers handle the messy parts.
- **No dependency injection framework.** `@Environment` for theme and
  `ModelContext` is sufficient.
- **No reactive networking layer.** This is an offline-first single-user
  app. There is no network.
- **No analytics SDK.** Privacy stance: zero data collection, zero
  trackers. See `PRIVACY.md`.
